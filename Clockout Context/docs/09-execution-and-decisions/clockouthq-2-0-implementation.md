# ClockoutHQ 2.0 implementation roadmap

**Status as of November 7, 2026:** Phase 0 audit and Phase 1 reconciliation completed. U08 / D22 authorized the documentation for Phases 2–6. U09 / D23 finalized decisions and the fresh-chat handoff. Every remaining implementation phase is pending separate authorization. This roadmap grants no permission to execute a phase or to build, publish, launch or contact.

The deliverable is a high-quality, personalized two-page website concept that can be prepared efficiently and used only with the founder’s approval. Use existing canonical procedures rather than duplicating them. The [website sales operating system](../04-offers-and-sales/website-sales-operating-system.md) owns acquisition and [the execution system](../07-tools-and-systems/execution-system.md#demo-authorization-and-enforcement) owns gates. The [Operations Manager specification](../07-tools-and-systems/operations-manager-spec.md) and [Demo Factory specification](../04-offers-and-sales/demo-factory-spec.md) own technical contracts. [Current state](../CURRENT_STATE.md) and [open decisions](../OPEN_DECISIONS.md) own business status and unresolved choices.

The reviewed Phase 0 plan combined the real-prospect and three-type pilot as Phase 5 and scheduling and scaling as Phase 6. These correspond to the supplied guide’s steps 5–6 and 7–8 respectively. The two earlier construction milestones retain their own approvals. Existing customer obligations and the dated cash review keep their priority.

## Phase 2 — Prove approval enforcement

**First authorized task:** Run a read-only Phase 2 preflight. Verify the actual checkout, existing tracker authority (OD13), and a candidate restricted research and founder-only boundary (OD21). Record observed capabilities, gaps and required approvals in the [checkpoint](../CHECKPOINT.md). Keep the live store and protected actions disabled if authority or isolation is unresolved. Request separate permission for any OS account, permission or connector change. Proceed to inert fixtures only within the new chat’s authorization.

- **Deliverable and files.** Add the small `systems/operations/` CLI, policy and store files listed in the Operations Manager spec. Build only inert build, preview and send stubs for this phase. Use local Python, the standard library, existing Context Mode and the quota guidance. Use scratch data for gate and recovery tests.
- **Prerequisites and authority.** Obtain Phase 2 implementation approval, confirm OD13 tracker ownership and decide the actual restricted runner boundary with Donovin. Obtain separate authorization before changing OS accounts, permissions or connectors. Keep the founder’s execution, protected data, build roots and credentials outside the research identity. If the boundary is unavailable, keep protected actions disabled.
- **Order.** Establish owner-only paths and restricted probe first. Define candidate, frozen payload, approval and attempt contracts. Implement transactionally checked transitions, grants and revocations, unique attempt claims, and reconciliation. Exercise the stubs from both identities. Document backup and restore before using operational data.
- **Exit evidence.** Prove each row in the enforcement matrix below with fixture actions and the actual restricted identity. A missing grant or boundary probe must prevent even a stub invocation. Record exact commands, observations and failures. Obtain founder review before relying on the system. No website templates or production adapter are needed to prove the gates.

## Phase 3 — Qualify, audit and stop at the brief

- **Deliverable and files.** Extend `systems/operations/research.py` and fixture tests. Use the existing qualification score, severity rules, project forms, and bounded research contract. Start with one fixture, then one authorized public batch of at most ten candidates, three detailed audits and two briefs. Start with one trade and town and cap each detailed audit at five public routes.
- **Skills and tools.** Use the workspace `dispatch` and relevant `local-seo-audit`, `gbp-optimization`, `local-competitor-analysis` and `client-deliverables` checklists for public observations. Use `brief` as a field reference and store state once. Treat Reference Library audit methods as attributed reference. Use supported public browsing with approved access. Keep Leadgen and provider tools deferred until their rollout trigger, terms, costs and authorization are confirmed. [Tool register](../07-tools-and-systems/tool-register.md#demo-pilot-routing)
- **Prerequisites and risks.** Phase 2 passes, Phase 3 public research is authorized, capacity and target area are confirmed, and collection/reuse terms are suitable. Distinguish missing facts from observed defects. No private accounts, outreach, website construction, paid calls or automatic imports from untrusted files.
- **Exit evidence.** Duplicate runs produce no duplicate candidate records. A fixture with no verified site preserves uncertainty. A dated mobile observation is reproducible. A stale claim or unresolved right is held or excluded. Each brief contains two page plans, evidence, assumptions and a visible stop at awaiting build approval. No protected adapter or website path was touched.

## Phase 4 — Approve and build the fictional master

- **Deliverable and files.** First provide a written design and QA brief for the master. After the explicit master build grant, implement the small `systems/demo-factory/` project and Playwright tests specified in the Demo Factory spec. Use fictional inputs, original or licensed assets, and one distinctive design with a complete owner report and simulated inquiry.
- **Skills and tools.** Use the website playbook and approved frontend builder, frontend testing, design review and accessibility skills where relevant. Use `build-local-site` only as reference. Verify supported Node and package versions, lockfile integrity, licenses and browser readiness before installation. Approve dependencies separately. Add extra audit tools only on the recorded trigger.
- **Prerequisites and risks.** Phase 3 supplies a realistic brief shape. Approve the exact master scope before writing any website source, component or scaffold. Keep the first artifact local and keep starter/CMS bulk generation out. Scope drift, generic design, incorrect route counts and live interactions fail the phase.
- **Exit evidence.** Exactly two routes on a reproducible build. Pass the browser, artifact, factual and visual checks in the Demo Factory spec. Record QA and Donovin’s visual review against the artifact digest. Publication is an independent decision and is unnecessary to accept the local master.

## Phase 5 — Prove the prospect pilot and economics

- **Deliverable and files.** Reuse the existing research, CLI, Factory, forms and playbook. Start with one real prospect and then cover three distinct types in total, including an appointment-led business and two distinct service contexts. Keep prospect data, assets and review records in private storage. Extend code only to resolve a demonstrated pilot limitation after applicable authorization.
- **Approvals and prerequisites.** Require each prospect’s build approval. Obtain separate publication approval after QA for each pilot artifact, exact destination and access policy. Verify existing host, HTTPS, release/withdrawal path and working Clockout CTA. Obtain separate outreach approval of the exact verified preview and payload. Confirm sender, opt-out, receipt lookup and a successful founder-owned test before enabling real outreach. Any test contact or integration use still needs applicable authorization. Production construction and launch stay separate.
- **Risks and execution.** Hold missing rights, unsupported business claims, unsafe preview exposure, sender ambiguity, changed messages or preview versions, suppression and uncertain send results. Use Donovin’s voice workflow for the message only when authorized. Reconcile time, direct spend, revisions and actual outcomes. Take founder review at each approval boundary.
- **Exit evidence.** For each approved prospect, record distinct business-specific composition and findings, passed QA, exact approvals and release verification if published. For approved outreach, distinguish released package, verified Sent/provider acceptance, delivery, reply and later sales. Demonstrate one full authorized path before calling the outreach loop proven. If authorization is pending, record the hold and leave the corresponding pilot result unverified.

## Phase 6 — Schedule bounded research and review results

- **Deliverable and files.** Reuse the Phase 3 research entry point and add operator scheduling/recovery instructions to `systems/operations/README.md` and relevant tests if needed. Define one separately authorized project-scoped job. It produces staged research records, brief reviews and a short run report. No privileged adapters or duplicate tracker.
- **Prerequisites and authority.** Manual pilot and isolation evidence pass. Donovin approves cadence, caps, cost and the actual scheduler environment. Use the real restricted identity and verify the machine/app requirements. A normal developer worktree or an owner-privileged desktop profile is not an adequate isolation boundary. Keep manual execution if scheduled isolation cannot be proven.
- **Verification.** Run a fixture from the scheduled identity. Check an absent machine/app or interrupted run does not count as success, a duplicate window produces no duplicate entries, a concurrent lease fails closed, and permissions prevent writes outside staging and access to credentials or any privileged action. Preserve pending approvals and record blockers and recovery. Pause repeated failures for review.
- **Scaling.** Begin with Phase 3 caps. Increase volume only after measured quality, build effort, costs and delivery capacity support it. A higher ceiling of 30 candidates and ten briefs is a review threshold, not a target or authorization. Do not introduce paid fallback, unattended privileged execution, or a custom factory skill without specific evidence and applicable approval.

## Verification matrix

| Scenario | Required evidence before enabling the affected operation |
| --- | --- |
| No build grant, wrong or edited brief, master without its own grant, expired/revoked grant, or another prospect in a batch | No build dispatch, website source write or directory creation. Log the denial. A valid exact grant reaches only the inert stub in Phase 2. |
| Restricted runner tries direct write, approval store mutation, symlink or path escape, owner command, authenticated connector or alternative messaging/publication path | OS and capability checks deny access independently of the prompt. Test the same boundary for the scheduled identity. |
| Approved input changes after review, a path changes, or another process attempts concurrent use | Mismatch fails before dispatch. The unique claim prevents duplicate execution. An interrupted claim requires evidence-based reconciliation. |
| Pilot publication missing approval, artifact differs, or destination changes | No publication dispatch. A future combined grant works only for its explicitly authorized preconfigured environment after QA and artifact binding. Production launch is never implied. |
| Failed QA, stale release, missing outreach approval, edited message, opt-out, duplicate attempt or wrong recipient | No outreach release or send. Accepted exact fixture exercises the inert adapter once. |
| Crash or uncertain send | Pending/uncertain remains visible. No blind retry and no contacted result without actual receipt evidence. |
| Private backup and restore | Restore a fixture into a separate directory. Verify records and sealed artifacts before switching over. Preserve the original. |
| Demo, prospect and schedule acceptance | Keep build/QA, release, contact and scheduler evidence separate. Reuse each phase’s exit checks and record pending items explicitly. |
