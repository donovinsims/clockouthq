# Operations Manager implementation specification

Status: documentation complete, implementation pending separate authorization. [Execution policy](execution-system.md#demo-authorization-and-enforcement) owns approval requirements. The [implementation roadmap](../09-execution-and-decisions/clockouthq-2-0-implementation.md) owns sequencing and verification.

## Runtime and responsibilities

- **Donovin** owns priorities, Attio sync policy and reconciliation, grant issuance and revocation, privileged command invocation, pilot release, sending, and go/no-go reviews. A specific approval is recorded before its associated action.
- **Research runner** reads permitted public sources and submits structured observations and briefs. It cannot approve, write site source or build outputs, publish, contact, or mutate the authoritative tracker. Use a separate restricted identity or demonstrably equivalent OS-enforced boundary. A research job can be manual or scheduled under the same restrictions.
- **Founder-operated CLI** is the only managed path to ingest, approve, revoke, claim, reconcile, and release work. It validates data and current state before dispatch. Run it from a founder-controlled environment with trusted executable paths, a sanitized environment, and no agent-writable commands, hooks or credential stores. Research and build identities cannot invoke it with founder authority.
- **Approved builder** gets the frozen public-safe input, reviewed template revision, scoped workspace and local QA instructions only after a build grant is checked and claimed. It has no approval, preview publishing, production, or messaging credentials. The founder checks visual QA and authorizes release separately for every pilot preview.

Start with one standard-library Python CLI, private SQLite and owner-private artifact files under the approved local toolkit directory outside Git. Preserve complete lead research, prospect records, raw evidence and screenshots, findings, briefs, task states, approvals, execution logs and CRM reconciliation records locally. Back up and restore the database and artifact files as one consistent set. Attio is the existing CRM and receives bounded outbound projections under [OD13](../OPEN_DECISIONS.md#od13--p2). Attio outages must leave all local operations usable. No second operational tracker is needed.

Keep verified financial records in the existing private financial system and store only references and confirmed aggregates here.

Use the existing store and tests for outbox, binding and attempt state. Research, build and outreach entry points do not carry Attio credentials or call CRM synchronously.

## Data and operator contracts

| Record | Minimum durable fields and invariants |
| --- | --- |
| Candidate and run | Stable prospect ID, normalized identity and duplicate keys, qualification, stage and blocker, next action, owner; run ID, stage, outcome, dates, evidence references and capped usage. Match source IDs or corroborated domain/name/location combinations; send ambiguous matches to review. |
| Evidence and brief revision | Source pointer, date and context such as viewport, observation, confidence, provenance and reuse status. Store an immutable brief revision with versioned scope, supporting evidence, unknowns, rights, build inputs and review caps. Keep sensitive observations and recipient data outside the renderer projection. |
| Authorization | Grant ID, operation, founder identity, target ID, revision and input digest, permitted scope and environment where applicable, issue/expiry times, status and claim reference. A batch names each exact target and revision. Use seven days as the default expiry and allow the founder to shorten it. |
| Artifact, QA and release | Build ID, source/input digests, artifact manifest and digest, test results, founder visual review, preview environment and verified release reference. Preserve version history so a newer artifact never silently replaces a reviewed one. |
| Attempt, suppression and events | Operation, deterministic idempotency key, claim time, progress, outcome, and evidence or error; suppression key, time and reason; append-only events for decisions and transitions. Provider acceptance, verified Sent, delivery and reply remain distinct. |

Use UTF-8 canonical JSON with stable key order, a fixed serialization for the supported data types, and SHA-256 for versioned approval payloads. Hash actual sorted artifact paths and bytes and check the sealed manifest before use. Freeze inputs on review. Do not hash a mutable path or draft in place of its contents. Store dates in UTC with an explicit offset and render founder review dates in America/Chicago. Validate schema and bounds, escape untrusted values in displays and renderer inputs, and reject symlinks, absolute paths and path traversal in submissions and artifacts. Use owner-controlled handles to look up targets and destination settings. Research values cannot supply shell commands, adapter paths, egress credentials or arbitrary destinations.

| Command surface | Input and output |
| --- | --- |
| Ingest and review | Import a validated candidate/brief file or show an immutable review packet with ID, revision, digest, blockers and next action. Rejected imports change no authoritative business record. Untrusted runners write only to isolated staging, and the owner process imports verified schema records. |
| Approve and revoke | Founder explicitly confirms the exact displayed operation and payload. Append a grant or revocation event. A superseded brief, changed material input or payload needs fresh review. |
| Build, publish and outreach | Check the current grant and prerequisites, claim a unique operation attempt, then dispatch to the applicable enabled adapter. Default to refusal. In Phase 2 use inert test adapters for every privileged path, including publication. |
| Reconcile and report | Inspect last verified event, display blockers, and record actual artifacts or provider evidence. Recover without reissuing a side effect by default. Generate a read-only scorecard from the tracker. |

## State, authorization and recovery

Use a single prospect workflow with recorded intermediate results. The normal route is research → audited → awaiting build approval → building → QA passed → awaiting preview approval → preview verified → awaiting outreach approval → contact recorded → interested, declined, opted out or closed. Preserve blocked, failed, deferred and uncertain outcomes. For a separately authorized future combined grant, the release capability is part of the build approval, but QA and preview verification remain separate steps. Production construction and launch use their own authorized workflow under the existing paid scope and delivery process.

1. Re-read the grant, prerequisite state, exact digests and suppression where applicable. Reject expired, revoked, consumed, wrong-operation, wrong-target, wrong-scope and mismatched revisions. Claim a unique attempt in the same transaction. Use transactional uniqueness to prevent concurrent claims. Commit the claim before doing work; do not hold the database transaction open over an external action.
2. Recheck the protected inputs and any revocation before dispatch. The grant is single-use for the claimed operation. One local rebuild or QA repair under the same claim is allowed when it preserves the approved inputs and scope and the grant remains valid. New evidence affecting rendered facts, changed template revision or scope, and a new operation after expiry require a new grant. Pause on a partial or indeterminate prior attempt; revocation after external dispatch requires reconciliation and, if applicable, an authorized removal.
3. For pilot preview release, require a separate grant after QA naming the sealed artifact and destination. A later founder-issued combined grant must name a preconfigured environment and authorize release explicitly. Bind the eventual artifact to that exact approved build and reject missing QA, a changed environment profile, path drift or an artifact swap. Check both deployed pages and the release identifier or asset hashes before setting preview verified. Keep any destination or access changes outside routine execution.
4. For outreach, freeze the verified preview reference, recipient, sender, channel, subject, body and attachments. Check suppression and duplicate intent immediately before release. For the pilot, an owner-only command may release the frozen payload into the founder’s existing mail workflow; only Donovin controls that mailbox. Match the actual Sent record or provider result before recording contact. An adapter may be added later under separate authorization after an owner-controlled test. A timeout, ambiguous result or crash after dispatch blocks retries until the founder reconciles it. If the exact payload changes, invalidate the release and request a new decision. An owner’s direct actions outside the managed workflow are outside the system’s enforcement boundary.

Treat imported observations and public pages as untrusted data. Disable privilege escalation, inherited browser sessions, account-backed browser or MCP connectors, external messaging and deployment egress in the research environment. Allow only needed public read access; enforce destination and redirect rules against local/private targets and bound request and content size. Use a capability probe from the actual identity, including absolute paths, symlinks and alternate connector paths. If a boundary cannot be proven, keep the affected command and scheduled task disabled. A prompt rule or permission check inside an unrestricted account is insufficient.

## Research and automation contract

1. Use the [qualification and audit process](../04-offers-and-sales/website-sales-operating-system.md). Start with one trade/town, up to ten candidates, three detailed audits, five public routes per audit and two briefs. Prioritize customer task friction and real delivery capacity. No authenticated site actions, referral requests, live form submissions, personal contact guesses or prohibited collection.
2. Capture dated, attributable facts and classify them as verified public observations, proposed improvements, unknowns or owner-access requirements. For a missing official website, record which sources were searched and keep the status unverified. Use public data under the source’s collection, attribution and reuse rules. Flag unresolved rights and identity instead of filling the gap with invented claims.
3. Validate candidate identity, duplicate keys, evidence links and brief completeness before ingestion. Hand off a versioned review packet with both page plans, strongest supported findings, image rights, simulation behavior, risks and effort cap. Stop at awaiting build approval. The [tool register](tool-register.md#demo-pilot-routing) owns skill selection and paid-provider limits.
4. Schedule only after the manual pilot, with explicit founder approval of profile, cadence, capacity and stop conditions. Run the same restricted research path as a single bounded job. It submits staged records for validated ingestion and emits a short run summary. Use a unique run/window key, one active lease, no catch-up flood, and a visible hold on repeated failures. Preserve pending briefs and approvals. Use the desktop scheduler only if the actual profile meets the isolation requirements and the machine, app and project are available. Otherwise retain the manual entry point. [Codex automations](https://learn.chatgpt.com/docs/automations?surface=app)

Report prospects researched, qualified, briefs approved, builds/QA, effort and direct costs, verified contacts and positive replies, conversations, deposits and paid delivery outcomes from actual events. Record test/model usage only where measured. Keep local backup, restore and scheduler evidence private and show pending or uncertain work explicitly.
