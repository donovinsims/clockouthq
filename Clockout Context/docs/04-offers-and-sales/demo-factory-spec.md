# Demo Factory implementation specification

Status: documentation complete. Any master-template or prospect construction requires prior explicit founder approval. The [website sales operating system](website-sales-operating-system.md) owns the acquisition sequence. The [website playbook](clockout_website_playbook_2026.md#pre-sale-demo-mode) owns design quality, and the [execution policy](../07-tools-and-systems/execution-system.md#demo-authorization-and-enforcement) owns permissions.

## Deliverable and construction boundary

Build one independent static artifact per approved brief. The master uses fictional data. A prospect build uses one approved business projection. There are exactly two first-party content routes, `/` and `/opportunities/` relative to the approved preview base. Navigation links the two routes and relevant landing-page sections. Shared typography, header, footer, disclosure, and navigation make them feel like one site. Asset files are allowed. There is no generated location, service, contact, campaign, or other content page.

Use a minimal Astro/TypeScript project and component CSS. Prefer Astro static file routes and relative navigation compatible with an authorized base path. Use only a small local script for simulated inquiry and chatbot behavior. No server, CMS, AI calls, analytics, real lead capture, or provider dependencies in the initial design. One reviewed, pinned lockfile and one supported Node runtime are prerequisites to the first approved build. Inspect licenses and asset permissions before reuse. Use the relevant patterns from installed skills. The full-site generator and its programmatic routes and deployment integrations are out of scope. [Astro routing](https://docs.astro.build/en/guides/routing/) · [Playwright setup](https://playwright.dev/docs/intro)

## Input and page contracts

The [Operations Manager](../07-tools-and-systems/operations-manager-spec.md) freezes and validates the private brief. Pass only a versioned, public-safe projection of approved values to the builder. The projection identifies the exact brief/revision and contains display business name, verified services and geography, brand and layout direction, reviewed copy, CTA and approved Clockout contact route, permitted proof and assets, sourced findings, approved comparisons, and scripted interaction content. Validate required values and allowed enums before rendering. Use safe local asset references, reviewed link destinations and escaped text. Omit optional unsupported claims or label proposals where useful. Block a material identity, scope, rights, privacy or CTA issue. No prospect inbox address, owner-only data, unapproved public screenshot, private report notes, credentials or unverified personal information goes into page or asset output.

| Page | Content and behavior |
| --- | --- |
| **Business landing page** | Explain the actual service, geography and primary action on the first mobile screen. Use verified service details, relevant proof with consent, a representative image or licensed asset, and a business-specific composition. Include a primary CTA, service area or equivalent useful context, and credible contact details when approved. Show the visible unofficial-concept disclosure. A clearly marked local simulation handles quote/inquiry and chatbot actions using approved facts. It accepts no personal information, sends no messages, and makes no outbound interaction calls. |
| **Your Growth Opportunities** | Lead with the strongest supported findings and the proposed design response. For each, show the dated observation, public evidence where permitted, customer task affected, design or SEO improvement, and confidence/unknowns. Separate public local SEO and GBP facts from items requiring owner access. Use a before/proposed pair only when the source asset can be reused. If an official site was unverified, state what was searched. Keep the commercial handoff clear, including what is simulated or separately scoped and a verified Clockout CTA. |

Do not imply certification, affiliation, ranking movement, sales gains or lost revenue without evidence. Keep the design tailored with specific copy, typography, content hierarchy, and imagery suited to the business. For the three-type pilot, require evidence that the design choices and structure reflect each brief. Avoid a fixed quantity of findings, token visual substitutions, and generic review claims.

## QA, release and handoff

1. **Build and artifact check.** Use the pinned build command after authorization. Produce a sealed artifact with a sorted manifest and content digest, plus build log and approved input/source references. Fail on unexpected HTML routes, path escape, private material, credentials, embedded external trackers or unapproved hosts/assets. Serve locally for QA.
2. **Repeatable browser QA.** Verify 390 px and 1440 px screenshots and 320 px reflow, route navigation, anchors, CTAs, menu, keyboard, focus, contrast, and console/network behavior. Assert that the chatbot and inquiry simulation never post a real inquiry or collect personal data. Exercise the approved path and a bad input or missing asset. Check both route titles, disclosure and preview indexing controls. Use lab measurements only with recorded conditions. A score alone cannot qualify a release.
3. **Factual and founder review.** Confirm identity, services, area, rights, source dates, evidence and honest impact wording. Donovin reviews both pages for visual quality, mobile clarity, plausibility and personalization. Record the test results, build ID and approval evidence. Treat wrong facts, rights or privacy issues, blocked keyboard or primary tasks, broken navigation and unexpected requests as release blockers. Allow one in-scope local repair under the active build claim. Re-run affected checks and founder review against the final artifact. Reapprove if scoped inputs or the approved template revision change.
4. **Preview release.** The pilot requires a separate approval for the exact QA-passed artifact and destination. Use a verified existing static destination with HTTPS and a removal path. For an unlisted public-safe preview, use an unguessable route, exclude it from sitemaps and apply `noindex`. Crawler blocking can prevent a crawler from seeing that directive. Restrict access through actual authentication when needed. Verify access policy, both live pages, disclosure, indexing controls and deployment identity before outreach review. If the host cannot supply the approved behavior, hold release. [Google indexing controls](https://developers.google.com/search/docs/crawling-indexing/block-indexing) · [WCAG 2.2](https://www.w3.org/TR/WCAG22/)
5. **Handoff.** Provide the sealed artifact reference, verification summary, screenshots, verified preview and principal finding to the founder for outreach review. The [working forms](../10-reference-and-archive/templates/website-project-forms.md#two-page-demo-qa) supply the review record. The paid offer remains separately scoped. Preserve client production build, acceptance, payment and launch controls.
